I · In 60 Seconds

This summer I was a software engineering intern at Gusto, on the team that builds tools for customer support. One of them is an internal AI assistant that support advocates use to ask questions while handling customer cases.

Before I joined, an advocate had to know exactly what to ask, and the answer came back as a chunk of text. A huge chunk of text, while a customer waited on the line. My project was to make the assistant proactive. By the end of the summer, it could do three new things: ask a clarifying question when it isn't sure, show its answer as interactive UI elements, like a table or cards, instead of a paragraph, and act, starting with drafting an email the advocate can send in one click.

II · How It Works

A language model only outputs text. So how does it produce a button?

It doesn't, directly. The model is given tools, which are functions it can call, each with a schema that spells out its arguments. When the assistant decides a question is ambiguous, it doesn't write "Did you mean A or B?" as text. It calls a tool with a structured list of options, and that call streams to the frontend as data, not text.

On the frontend, I built a registry that maps each tool to a component. When a tool call arrives, the interface renders the match: clickable pills, a table, cards, or an action button. Clicking a pill sends that option back to the model as the next message, so the conversation continues without the advocate typing anything.

If you've used Claude or another AI chat app, you've probably seen this pattern. When it's unsure what you want, it asks a multiple-choice question, you pick A, B, or C, and it answers with your choice in mind. It's essentially the same idea.

I didn't want the pills to be a one-off, so I built the layer they run on. The registry works as a dictionary, where each entry pairs a tool's name with the component that draws it. To teach the assistant something new, say a date picker, an engineer builds the tool and its component, then adds one line to the registry to connect them. Nothing else in the interface has to change.

IV · What I Learned

Watch people work before writing code. This project took me beyond writing code. I got to sit in on live calls and watch people that actually use the assistant. Three problems kept coming up. First, the assistant guessed instead of asking. Second, plain text was slow to scan mid-call. Third, advocates had to switch tabs constantly. Sending one email could mean three tools and pasting the subject and body by hand. Watching the users directly shaped what I built.

Test it in the room. I tested the features I built at an onsite, where advocates used them on live calls while our team watched. One told us it would save them a lot of time. Hearing that from people I'd been watching work for weeks was one of the best moments of my summer.

Work with people you enjoy. The environment matters a lot. I was surrounded by supportive people I liked being around, and we came up with a lot of ideas along the way. I had a great time building this, and I think the work was better for it.

Learn the system, don't just prompt it. With AI, it's tempting to tell Claude what to build and move on. At Minerva, my university, we spend a lot of time on the science of learning, and one of the earliest lessons I implemented during my internship was to use AI to understand, not just to produce. When I was ramping up on an agent backend I'd never touched before May, I used Claude's learning mode to understand the architecture before writing much code. It was slower at first, but I moved faster later because I knew what I was writing.
